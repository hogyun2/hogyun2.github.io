Co-NavGPT 뜯어보기 — 키워드 통계에서 공개 코드까지

2026년 7월 27일 Research 20분 읽기

Co-NavGPT: Multirobot Cooperative Visual Semantic Navigation Using Vision Language Models
Bangguo Yu, Qihao Yuan, Kailai Li, Hamidreza Kasaei, Ming Cao · IEEE Robotics and Automation Letters, Vol. 11, No. 2, February 2026

세미나 준비하면서 이 논문의 본문 어휘 분포를 뽑아봤습니다. 논문이 실제로 무엇에 지면을 쓰는지는 초록의 주장보다 어휘 빈도가 더 정직하게 보여주는 경우가 있어서, 제목~결론 구간을 통째로 세어봤습니다. 참고문헌 목록과 페이지 워터마크는 제외했고, 단수/복수는 하나로 합쳤습니다.

세어놓고 보니 상위 어휘가 네 갈래로 깔끔하게 갈렸고, 그 네 갈래가 논문의 파이프라인 순서와 그대로 맞아떨어졌습니다. 그래서 이 글은 통계에서 출발해 구현까지 내려갑니다. 빈도 통계 → 개요 → 방법론 상세 → 비판적 검토 네 부분입니다.

방법론 부분은 논문만 읽고 쓴 게 아니라 저자들이 공개한 구현 (Co-NavGPT2)을 한 줄씩 대조하며 확인했습니다. 논문 서술만으로는 애매했던 부분이 코드에서 풀리기도 했고, 반대로 논문에 없거나 어긋나는 구현 사실도 여럿 나왔습니다.

PART 2

개요 — 한 문장, 네 질문, 두 주기

상세로 들어가기 전에 전체 그림을 세 각도로 잡습니다.

네 갈래를 한 문장으로

앞서 센 네 갈래를 논문의 파이프라인 순서대로 이으면, 논문 한 편이 한 문장이 됩니다. 밑줄 색은 위 클러스터 색과 같습니다.

Co-NavGPT, 한 문장

여러 로봇이 각자 만든 부분 맵을 로봇 상태와 프론티어 영역이 인코딩된 하나의 전역 맵으로 합친 뒤, VLM이 전역 플래너로서 각 로봇에 프론티어를 배분해, 별도의 과제별 학습 없이 미지 환경에서 목표 물체를 협력 탐색하도록 하는 프레임워크.

멀티로봇 협업 → 맵·프론티어 탐색 → VLM·추론 → 내비게이션 과제

네 개의 질문

이 한 문장은 곧바로 네 개의 질문으로 쪼개집니다. 각 구절이 "그래서 어떻게?"를 남기기 때문입니다. 아래 답은 논문이 아니라 코드로 확인한 것이라, 논문 서술과 어긋나는 대목이 섞여 있습니다.

Q1
여러 로봇의 부분 맵을 어떻게 합치나?

시뮬레이션에서는 합치기만 하고 정합은 하지 않습니다. 모든 로봇이 같은 지점에서 출발하고 시뮬레이터가 정확한 자세를 주므로 포인트 클라우드를 그냥 더합니다. G-ICP는 실환경에서만, 그것도 카메라가 아닌 LiDAR 맵으로 탐색 시작 전 1회만 돕니다.

Q2
맵에 무엇을 인코딩하나?

3D 클라우드를 obstacle · explored · top-view 세 채널로 나누는데, VLM에게는 top-view 한 장만 갑니다. 나머지 둘은 프론티어를 계산하는 내부 재료입니다. top-view 위에 로봇 위치(검정)와 프론티어(빨강)를 그려 넣고, 후보 하나당 이미지 한 장씩 만듭니다.

Q3
VLM은 어떤 기준으로 배분하나?

프롬프트가 요구하는 기준은 협력적 탐색과 의미적 관련성 둘입니다. 다만 로봇별 거리를 시스템이 계산해 주지 않습니다. FMM이 이미 정확한 측지거리를 갖고 있는데도 넘기지 않고, VLM이 이미지에서 눈대중으로 판단하게 둡니다.

Q4
어떻게 "협력적"으로 탐색하나?

협력이 성립하는 지점은 셋입니다 — 각자 본 것이 하나의 전역 맵으로 모이고, VLM이 서로 다른 프론티어를 줘 중복을 줄이며, 한 로봇이라도 목표를 찾으면 에피소드 성공입니다.

두 개의 주기

구조를 이해하는 열쇠는 루프가 두 박자로 돈다는 것입니다. 지각과 이동은 매 스텝, VLM 호출은 25스텝에 한 번입니다. 나머지 24스텝 동안 로봇은 이미 받은 목표를 향해 스스로 움직입니다.

매 스텝
① 지각 → 3D ② 3D → 2D 맵     ⑤ 주행
25 스텝마다
    ③ 프론티어 추출 ④ VLM 배분  

VLM = "어디로" (global planner) · FMM = "어떻게" (local policy). 논문이 밝힌 이유는 VLM이 고수준 계획엔 강하지만 세밀한 저수준 제어엔 신뢰도가 떨어진다는 것이고, 이 분리가 실환경 5 FPS의 근거이기도 합니다.

PART 3

상세 — 데이터가 거쳐 가는 아홉 단계

각 단계의 입력과 출력을 따라가면 시스템이 실제로 무엇을 주고받는지 보입니다.

단계 번호의 색은 앞의 클러스터 색과 같습니다 — 어느 갈래의 어휘가 그 단계를 설명하는지 표시한 것입니다. 순서대로 내려가면 네 색이 순환하는 게 보입니다.

매 스텝 · 로봇별 각 로봇이 독립적으로 보고 그린다
1

지각 · 검출 · 분할

RGB-D 이미지 + 자세 → 목표 물체 마스크

YOLO-World가 후보 박스를 찾고, Mobile-SAM이 클래스와 무관하게 마스크를 뜹니다. 논문은 열린 어휘(open-vocabulary) 검출기라고 소개하지만, 코드에는 6개 클래스가 하드코딩돼 있습니다.

self.classes = ["chair", "bed", "potted plant", "toilet", "tv_screen", "couch"]

여기에 wall도 floor도 없습니다. 벽과 바닥에는 마스크가 붙지 않고, 따라서 시스템 어디에도 "이건 벽이다"라는 정보가 존재하지 않습니다. 뒤에서 다시 중요해지는 사실입니다.

2

역투영 — 2.5D를 3D로

depth + 내부 파라미터 + 자세 → 두 종류의 포인트 클라우드

흔히 RGB-D를 3D라고 부르지만 정확히는 2.5D입니다. depth 이미지가 가진 건 화면 좌표(픽셀)와 거리뿐이고, 실제 공간에서 몇 미터 옆인지는 아직 모릅니다. 카메라 내부 파라미터로 펴야 비로소 3D 점이 됩니다.

x = (u - cx) * depth / fx # 역투영: 픽셀 → 카메라 좌표 y = (v - cy) * depth / fy z = depth pcd.transform(camera_matrix_T) # pose로 전역 좌표계 이동

초점거리 fx를 모르면 depth 이미지는 기하학적으로 무의미합니다. 같은 픽셀이라도 화각이 넓은 카메라면 더 옆에 있는 점이 되기 때문입니다. 자세를 곱하는 이유도 같습니다 — 카메라 기준 "앞 2m"가 방 안 어디인지는 로봇이 어디서 어느 방향을 봤는지를 알아야 정해집니다.

여기서 클라우드가 두 갈래로 갈립니다. 서로 독립입니다. 하나는 마스크를 써서 목표 물체만 담고, 다른 하나는 마스크 없이 장면 전체를 담습니다. 벽과 바닥은 후자에 들어갑니다 — 이들이 없으면 장애물 회피도 프론티어 추출도 불가능해집니다.

object_pcd ← 마스크 O · 목표 클래스 일치 · 신뢰도 통과 point_sum ← 마스크 X · 조건 없음 · 장면 전체(벽·바닥 포함)

이어서 DBSCAN이 주변에 동료가 없는 점을 버립니다. 물체 경계에서 앞뒤 depth가 섞여 생기는 허공의 점, 유리·금속 반사로 튄 점이 여기서 걸러집니다.

pcd.cluster_dbscan(eps=0.02, min_points=10)
3

전역 맵 병합

로봇별 클라우드 × n → 하나의 전역 클라우드

여기서부터 로봇들은 같은 지도를 봅니다. 협업이 성립하는 출발점입니다. 그런데 어떻게 합치는지는 시뮬레이션과 실환경이 전혀 다릅니다.

point_sum += agent[i].point_sum # main.py — 이게 전부

HM3D 실험에서는 정합(registration)을 하지 않습니다. 모든 로봇이 같은 지점에서 출발하고(방향만 다름) 시뮬레이터가 정확한 자세를 주므로, 처음부터 같은 좌표계 위에 있습니다. 합치기는 덧셈 한 줄입니다.

멀티로봇 SLAM에서 어려운 부분은 원래 정합입니다 — 서로 어디 있는지 모르는 로봇들의 상대 변환을 찾고 드리프트를 보정하는 것. 그 문제가 실험 설정에서 발생하지 않습니다. G-ICP는 실환경에서만 등장하고, 대상도 카메라가 아닌 LiDAR 맵입니다.

'/robot1/Laser_map' ┐ '/robot2/Laser_map' ┴→ G-ICP → static TF (시작 전 1회)

StaticTransformBroadcaster인 점이 결정적입니다 — 한 번 계산해 고정하고 주행 중 재정렬하지 않습니다. LiDAR를 쓰는 이유는 정합 정확도 때문입니다. 360° 맵은 구조가 뚜렷해 시야 좁은 RGB-D보다 ICP가 안정적으로 수렴합니다.

4

2D 맵 3채널 생성

전역 3D 클라우드 → obstacle · explored · top-view

24×24m를 5cm 격자로 나눈 480×480 맵입니다. 좌표 규약을 먼저 짚어야 하는데, Open3D/Habitat은 y축이 위쪽입니다. x와 z가 바닥 평면이고 points[:,1]이 높이입니다.

카메라 높이가 0.88m, 밴드 폭이 1.30m이므로 경계는 이렇게 정해집니다.

z_min = 0.88 - 0.65 = 0.23 m z_max = 0.88 + 0.65 = 1.53 m obstacle ← 0.23 ~ 1.53m 밴드 안의 점 explored ← 1.53m 이하 모든 점 top-view ← 각 칸 최상단 점의 색 (z-buffer)

obstacle은 의미 판단이 아니라 높이 검사입니다. 벽이든 의자든 사람이든 커튼이든 밴드에 걸리면 똑같이 1이 됩니다. 시스템은 그게 무엇인지 끝내 알지 못합니다 — 앞서 검출 어휘에 wall이 없었던 것을 떠올리면, 어디에도 벽이라는 개념이 없습니다.

그래서 오류가 생깁니다. 책상은 상판이 밴드에 걸려 막힘으로, 낮은 문턱은 밴드 아래라 비었음으로, 유리문은 depth가 실패해 미탐색으로 잡힙니다. 보정 장치가 두 개 붙는 이유입니다.

obstacle_map[explored - obstacle == 1] = 0 # 다시 보니 비었네 obstacle_map[dilate(visited_vis) == 1] = 0 # 지나간 자리는 장애물 아님

두 번째가 특히 재미있습니다 — 내가 이미 통과한 곳이 막혀 있을 리 없다는 규칙인데, 높이 검사가 틀릴 수 있다는 걸 전제한 처리입니다.

top-view는 각 칸에서 가장 높은 점의 색만 남깁니다(z-buffer). 위에서 내려다볼 때 실제로 보이는 표면이 그것이니까요. 여기 담기는 건 의미 라벨이 아니라 원본 RGB 픽셀 색입니다. 그래서 라벨 없는 벽과 바닥도 색으로는 남고, VLM이 "타일 바닥이니 주방이겠군"이라고 추론할 재료가 됩니다.

25 스텝마다 · 전역 1회 어디로 갈지 다시 정한다
5

프론티어 추출

obstacle + explored 맵 → 후보 프론티어 최대 6개

먼저 칸의 상태를 정확히 정리해야 합니다. 두 채널의 조합으로 세 가지가 나옵니다.

explored=0, obstacle=0 → unknown 한 번도 안 봄 explored=1, obstacle=0 → free 0.23m 아래에만 점 = 바닥만 보임 explored=1, obstacle=1 → occupied 밴드에 뭔가 있음

두 번째 줄이 흥미롭습니다. free가 성립하려면 점이 있으면서 0.23~1.53m 구간에는 없어야 하니, 결국 바닥만 보인 칸이라는 뜻입니다. 그러면 프론티어의 정의가 아주 구체적으로 내려옵니다.

프론티어 = 바닥이 보인 곳과 아무것도 못 본 곳의 경계

거기까지는 갈 수 있고(바닥 확인됨) 그 너머는 모릅니다(미관측). 그래서 가면 새로 보입니다. 주의할 점은 unknown이 뺄셈으로 만들어지지 않는다는 것입니다 — 맵이 0으로 시작해 한 번도 채워지지 않은 채 남은 칸이 unknown입니다.

계산은 뺄셈인데, 빼는 대상이 면이 아니라 선입니다. 탐색 영역의 윤곽선(1픽셀)에서 부풀린 장애물을 빼면 벽에 닿지 않은 부분만 남습니다. 장애물 쪽을 굳이 부풀리는 건 두 채널의 픽셀이 정확히 맞지 않아, 그냥 빼면 벽을 따라 실오라기 같은 가짜 프론티어가 남기 때문입니다.

obstacle_map = cv2.dilate(obstacle_map, 7x7) # 벽 부풀리기 contour = max(contours, key=cv2.contourArea) # 탐색영역 최대 윤곽 drawContours(edge_map, contour, -1, 1, 1) # 1픽셀 선 target_edge = edge_map - obstacle_map # 선 − 벽 measure.label(target_edge, connectivity=2) # 붙은 칸끼리 묶기

묶인 덩어리 하나가 "갈 수 있는 방향 하나"(문 하나, 복도 하나)가 됩니다. 그 다음이 논문에 전혀 없는 부분입니다.

if props[i].area > 8: # 임계값 8셀 dict_cost[i] = props[i].area # ★ 면적으로 정렬 sorted(dict_cost, key=lambda x: x[1], reverse=False) # 오름차순 Goal_point.append(props[key].centroid) # 무게중심 = waypoint if i == 5: break # 최대 6개

frontier_0은 가장 작은 클러스터입니다. 거리와 무관합니다. 저장소에 거리로 정렬하는 함수(detect_frontier)가 따로 있긴 한데 어느 진입점에서도 호출되지 않습니다 — 실제로 도는 건 면적순인 Frontier_Det입니다.

6

프롬프트 조립

top-view + 후보 + 로봇 자세 → 이미지 N장 + 텍스트 1벌

이 논문에서 가장 특이한 설계입니다. 후보가 5개면 지도 이미지를 5장 만듭니다. 배경과 로봇 표시는 모든 장에 동일하고, 빨간 마스크와 좌상단 번호만 장마다 바뀝니다. 한 장에 후보를 전부 그리면 VLM이 "3번 프론티어"를 특정하지 못하므로, 장 단위로 쪼개 식별 부담을 없앤 것입니다.

img = top_view_map.copy() # 배경·로봇 = 모든 장 동일 img[dilate(frontier_i, 5x5)] = [255,0,0] # 빨간 굵은 선 img = np.flipud(img) # 상하 반전 (필수) write_number(img, pose, i) # 로봇 검정 / ID 빨강

빨강은 임의로 고른 색이 아닙니다. 논문이 인용한 "What does CLIP know about a red circle?" 계열의 발견 — 이미지에 빨간 표시를 그리면 VLM이 그 영역에 주목한다는 것 — 을 따른 mark-based visual prompting입니다. 굵게 부풀리는 건 JPEG 압축과 VLM 내부 리사이즈를 거치며 1픽셀 선이 사라지는 걸 막기 위함이고, flipud는 배열 인덱스가 아래로 증가하는 반면 지도는 위가 북쪽이라 필요합니다.

텍스트 프롬프트는 후보 수와 무관하게 한 벌이고, 코드에 통째로 하드코딩된 고정 템플릿입니다. 사용자가 주는 건 찾을 물체 이름 하나뿐입니다.

[{"role":"system", "content": system_prompt}, # 고정 템플릿 {"role":"user", "content":[ {"type":"text", "text":"two robots need to find a chair"}, {"type":"image_url"} x N ]}] # 후보 이미지
7

VLM 프론티어 배분

이미지 N장 + 목표 물체 → JSON 배분표 + 이유

판단 기준은 둘입니다. 협력적 탐색(로봇들이 흩어져 커버리지를 넓히도록)과 의미적 관련성(목표가 있을 법한 쪽으로). 두 번째가 VLM을 쓰는 이유 전부입니다 — "sink를 찾아라"면 침실 쪽보다 타일과 싱크대가 보이는 쪽을 고릅니다. 가까운 프론티어부터 가는 기존 방식은 못 하는 판단입니다.

출력이 JSON이어야 하는 이유는 그 답이 곧 좌표가 되기 때문입니다. 사람이 읽는 게 아니라 코드가 받아 즉시 실행합니다.

"frontier_1" → split('_')[1] → 1 → target_point_list[1] → [237, 194] → goal_map[237,194] = 1 # 로봇 출발

"로봇 0은 부엌 쪽이 좋겠습니다" 같은 문장에서는 좌표를 뽑아낼 수 없습니다. response_format={"json_object"}가 문법은 강제하지만 의미는 보장하지 못하므로, 키 개수와 ID 범위를 따로 검증합니다. 형식을 어기면 재시도하고 5회를 소진하면 전 로봇을 frontier_0으로 보냅니다.

여기서 짚어둘 설계 판단이 하나 있습니다. 로봇별 거리를 시스템이 계산해 주지 않습니다. 다음 단계의 FMM이 이미 정확한 측지거리를 갖고 있는데도 프롬프트에 넣지 않고, VLM이 이미지에서 눈대중으로 판단하게 둡니다. 그래서 VLM이 볼 수 있는 건 직선거리뿐이고, 벽을 돌아가야 하는 실제 경로 길이는 알 수 없습니다. 비교 대상인 Greedy와 Cost-Utility는 둘 다 실제 거리를 씁니다.

매 스텝 · 로봇별 받은 목표까지 알아서 간다
8

로컬 정책

목표 좌표 + obstacle 맵 → 행동 1개

목표점은 프론티어 덩어리의 무게중심입니다. 여기까지 가는 경로를 FMM이 짜는데, 그래프 탐색이 아닙니다. 노드도 엣지도 우선순위 큐도 없습니다.

dd = skfmm.distance(traversible_ma, dx=1) # 격자 전체에 거리값 argmin(내 주변) # 경사 따라 한 걸음

목표점에서 물이 퍼지듯 모든 칸에 "목표까지의 거리"를 한 번에 채우고, 로봇은 주변에서 값이 가장 낮은 칸으로 한 걸음씩 굴러 내려갑니다. A*가 노드 시퀀스를 만드는 것과 달리 결과물이 스칼라 장(field)이고, 8방향 제약이 없어 벽을 돌아가는 매끄러운 경로가 나옵니다.

이 방식의 부수 효과가 하나 있습니다 — 장을 한 번 풀어두면 어느 지점까지의 거리든 배열 인덱싱 한 번이라, 후보마다 경로 탐색을 돌릴 필요가 없습니다. 행동은 전진 25cm · 좌우 회전 30° · 상하 시선 · 정지 여섯 가지입니다.

VLM은 여기 관여하지 않습니다. 논문이 이유를 명시합니다 — VLM은 고수준 계획엔 강하지만 세밀한 저수준 제어에는 신뢰도가 떨어지기 때문입니다. 이 역할 분리가 실환경에서 5 FPS를 유지하는 근거이기도 합니다.

9

목표 발견 · 종료

목표 물체 포인트 클라우드 → 접근 후 정지

목표가 검출되는 순간 흐름이 바뀝니다. 프론티어 목표를 덮어쓰고, VLM은 더 이상 호출되지 않습니다. 탐색 모드에서 접근 모드로 전환되어 물체의 최근접점을 향해 직진합니다. 0.1m 안에서 정지하면 성공이고, 에피소드당 최대 500스텝입니다.

프롬프트 설계의 비대칭

시각 프롬프트와 텍스트 프롬프트가 논문에서 받는 대접이 크게 다릅니다.

같은 프롬프트인데 근거 제시와 검증의 정도가 다릅니다.
  선행 연구 인용 어블레이션
Visual Prompt [28]~[30] 명시 Obs. / DownSam.
Textual Prompt 없음 reason 제거만

시각 쪽은 "What does CLIP know about a red circle?"부터 조작·내비게이션 응용까지 계보를 밝힙니다. 반면 텍스트 쪽은 인용이 하나도 없습니다. "이렇게 설계했다"만 있고 왜 그렇게 했는지가 없습니다.

정작 코드에는 출처가 분명한 기법이 들어 있습니다. Let's think step by step. — 예시 없이 이 한 줄만으로 추론 성능이 오른다는 Kojima et al.(2022)의 zero-shot CoT입니다. 프롬프트 공학에서 가장 유명한 문장인데 인용도 없고, 논문에 실린 예시 프롬프트에는 아예 빠져 있습니다. 코드에만 있습니다.

Understand → Analyze → Decide → Justify 네 단계도 무출처입니다. 그리고 논문과 코드에서 순서가 다릅니다 — 코드는 Analyze가 먼저입니다. 출처가 있거나 순서에 원리가 있었다면 이렇게 어긋나기 어렵습니다. 네 단계 구조 자체를 검증한 어블레이션도 없습니다.

어블레이션에서 성능 기여가 가장 컸던 요소(reason 제거 시 최대 하락)가 하필 설계 근거가 가장 얇은 쪽입니다.

VLM은 무엇을 보고 고르는가

reason 필드가 판단 근거를 보여주니 해석 가능해 보이지만, LLM의 사후 설명이 실제 판단 근거라는 보장은 없습니다. 모델이 다른 이유로 답을 정해놓고 그럴듯한 설명을 덧붙이는 현상은 잘 알려져 있습니다. 즉 reason은 해석 가능성의 외형이지 검증이 아닙니다.

다만 완전한 블랙박스는 아닙니다. Obs. 어블레이션이 인과적 증거를 줍니다. 의미 정보가 담긴 top-view를 obstacle-only 맵으로 바꿨더니 성능이 떨어졌습니다 — 순전히 번호나 위치 편향으로 골랐다면 배경을 바꿔도 결과가 같아야 합니다. 해상도를 480에서 60으로 줄여도 하락 폭이 작았다는 것도 단서입니다. 세밀한 디테일이 아니라 큰 색감 덩어리를 보고 판단한다는 뜻이니까요.

그래서 정리하면 — "의미를 본다"는 확인됐지만 "어떤 규칙으로 고르는지"는 모릅니다. 거리를 실제로 고려하는지, 면적 큰 쪽을 선호하는지, ID 번호나 이미지 순서에 끌리는지 모두 미확인입니다. 특히 후자가 걸리는데, ID 순서와 이미지 전달 순서와 실패 시 fallback이 모두 frontier_0을 향합니다. 서로 상쇄되지 않고 같은 방향으로 겹칩니다.

코드 몇 줄이면 되는 실험 세 가지가 이를 상당 부분 해소합니다 — ID 무작위 셔플(번호 편향), 이미지 순서 셔플(위치 편향), 선택 ID 분포와 Greedy 일치율(실제 거리 고려 여부). 셋 다 논문에 없습니다.

그래서 기여는 무엇인가

"프롬프트를 잘 쓴 것"이 기여냐는 질문이 자연스럽게 나옵니다. 논문의 기여 목록에 프롬프트 설계는 없습니다 — 프레임워크, VLM 전역 플래너, 실험 셋입니다. 프롬프팅은 기여로 청구되지 않고 구현 수단으로 들어가 있습니다.

실제 기여는 프롬프트 문구가 아니라 인터페이스 설계에 있습니다. 셋입니다.

  • 생성이 아니라 선택으로 제한 — VLM이 좌표를 자유롭게 뱉으면 벽 속이나 미탐색 영역을 지목할 수 있습니다. 기하학적으로 유효한 후보만 만들어놓고 고르게 하면 그 실패가 원천 차단됩니다. 프롬프트 문구가 아니라 아키텍처 속성입니다.
  • 후보당 이미지 한 장 — 구체적 실패 모드(VLM이 "3번"을 특정하지 못함)에 대한 구체적 해법입니다.
  • 프론티어를 기하-언어의 접점으로 — 연속 공간을 VLM이 다룰 수 있는 이산 선택지로 바꾸는 추상화. 이게 논문의 실제 아이디어입니다.

RA-L 기준에서 실질적 성과는 4족 로봇 2대에서 5 FPS로 돌렸다는 것입니다 (비교 대상 [18]은 0.5 FPS 미만). 반면 "VLM으로 프론티어 고르기"라는 아이디어 자체는 2026년 기준으로 이미 붐빈 공간이라, 저널본의 증분은 개념적 신규성보다 멀티로봇 확장과 실환경 배치에 있다고 보는 편이 정확합니다.
